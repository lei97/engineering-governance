## 一个 Skill，五种工作模式

独立仓库维护通用规范，Skill 按任务加载相应规则。每个项目自行保存需求、授权依据与工程证据。五种模式共享六项原则，即边界明确、契约明确、过程透明、结果可验证、状态可恢复、复杂度隔离。任务可以切换模式，正式契约的变更仍由授权者裁决。[Skill 入口](../skills/engineering-governance/SKILL.md) · [治理原则](../specifications/principles.md) · [模式规范](../specifications/modes.md)

| 模式 | 用什么判断本次工作完成 |
| --- | --- |
| 标准 Standard | 对照已确认的需求与验收条件，给出符合性证据。首轮实验选用此模式。 |
| 创造 Creative | 用原型或实验检验假设，记录观察到的结果。 |
| 学习 Learning | 给出来源，并能用独立例子检验自己的理解。 |
| 逆向 Reverse | 用可复查的行为或代码证据支持候选契约，标出推断的边界。 |
| 修复 Repair | 复现预期与实际行为的偏差，用回归证据说明预期行为已恢复。 |

## 已确认的需求怎样进入 YAML

| 对话提出的四项契约 | v0.1 的落实方式 |
| --- | --- |
| 表达 | 一条需求一个可定位的记录。用 `statement` 和 `acceptance` 写清会改变验收判断的前提、行为、参照点和可观察结果。 |
| 解释 | 写明关键术语的含义和默认值的依据。材料缺少会影响结果的信息时，读者写“未规定”，交作者裁定。 |
| 验证 | 程序检查格式、类型和引用。作者依据事先写下的判定要点审阅独立答卷，检查分歧、遗漏及额外假设。 |
| 演进 | 意图发生变化时，由授权者确认并更新权威记录，沿引用复查受影响的契约、实现和测试，保留变更依据。 |

原包有六类记录，分别为来源 `source`、需求 `requirement`、契约 `contract`、产物 `artifact`、测试 `test` 与观察 `observation`。每条记录必填 `id`、`kind`、`title`、`status`、`statement`。需求另需 `origin` 指向来源记录，并提供至少一项 `acceptance`。需求的 `accepted` 只表示意图获授权确认。实现进度与验证结果各需相应证据。[记录 Schema](../schemas/knowledge.schema.json) · [真源规则](../specifications/source-of-truth.md)

原包限定每个 UTF-8 编码的 `.yaml` 文件只含一份顶层映射，叶子值按字符串读取。同一映射的键和同批记录的 ID 各自唯一。Skill 组织和格式约束所参考的 Claude、Agent Skills、YAML 与 JSON Schema 文档已列入原包。[YAML 表达规范](../specifications/yaml-profile.md) · [参考资料](../research/references.md)

对话末轮举过 `when`、`action`、`ensures`、`on_failure` 的例子。原包 Schema 会拒绝这些额外字段。首轮沿用现有字段，把已约定的前提、成功与失败结果写入正文或验收条件。是否增设字段，等答卷显示具体误读后再决定。[记录 Schema](../schemas/knowledge.schema.json)

## 原包样例暴露的一个分歧

需求 `REQ-001` 要求取消探索后，正式作品与**探索开始前**一致。测试记录 `TEST-001` 却比较**取消前后**的快照。设探索开始时作品为 A，取消前有人将正式作品改为 B。按需求文字验收会期待 A，按测试文字验收会期待 B。作者需要裁定这种更新是否允许，以及允许时应保留哪个版本。[需求样例](../examples/valid/REQ-001.yaml) · [测试记录](../examples/valid/TEST-001.yaml)

该需求能通过结构检查。`SRC-001` 记录指向的 `docs/exploration-notes.md` 未随包提供，包内的 `TEST-001` 也是一条测试描述。这个案例可用于练习发现歧义。作为正式实验输入，还需要项目作者提供真实依据并确认预期行为。[来源样例](../examples/valid/SRC-001.yaml)
